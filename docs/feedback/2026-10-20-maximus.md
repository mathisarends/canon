## What worked

Maximus already captures and encodes its remote Chromium display in a Hermes
GStreamer subprocess. The engine interface lets us preserve that peer and its
direct media path while adopting the package's signaling, admission, deadlines
and teardown. No upstream library or generated browser source was patched.

The endpoint `/api/v1/browser/{browser_id}/video` declares a server offerer sending
video only. Admission authenticates the cookie in a short unit of work, checks
origin and account/login ownership, then returns a `BrowserVideoTrack` describing
the remote stream. No database session remains open for media. The session expires
with its login. The existing `BACKEND_BROWSER_WEBRTC_ENABLED` switch still applies.

`BrowserVideoEngine` forwards offers, answers, candidates and actual GStreamer
connection-state events. Sending an answer is not treated as a connected peer.
Unsupported restart, renegotiation, channels and track operations reject explicitly.
Stats expose known connection state and leave native RTP metrics absent.

The generated TypeScript runtime replaces handwritten SDP/ICE sequencing.
`TurnRestCredentials` replaces our duplicated coturn HMAC construction, preserving
settings and the injected clock. Canon 0.5.5's shutdown order keeps Hermes and
Dishka resources available while the WebRTC router closes its sessions.

## Friction and proposed abstractions

| Priority | Observed integration work | Proposed upstream improvement |
| --- | --- | --- |
| High | A remote, send-only adapter implements the complete engine peer interface, including methods that always reject. A track descriptor carries the selected Hermes stream into the engine. | A documented remote-engine example, optional capability interfaces or a small send-only adapter base; an explicit per-session engine/resource binding. |
| High | `WebRtcRouter.session` has no `raises` parameter or Canon router integration. We register admission failures in the feature's Canon `ErrorRegistry`, allowing the session factory to propagate application exceptions without HTTP mapping in the handler. | A Canon integration with declarative admission errors, registry membership checks and generated contract metadata. Keep pre-accept HTTP problems distinct from post-accept WebRTC protocol errors. |
| High | Transport readiness does not prove that a picture is displayed. Maximus still polls browser `framesDecoded` and falls back after eight seconds without progress. | An optional client media-health observer with separate first-frame and ongoing-stall deadlines, independent of fallback UI. |
| High | A Hermes subscription owns each viewer. Global stop during cleanup could terminate an existing viewer when a second viewer was rejected. Cleanup now closes only its own subscription. | A documented lease/async-context-manager pattern for remote peers, including concurrent admission and cancellation before an offer. |
| Medium | The remote engine has connection state but no native RTP statistics. | Document partial stats and a structured remote-stats bridge; keep missing values explicit. |
| Medium | Browser WebSocket admission failures hide HTTP 401/403/404 from the runtime. | An optional short-lived ticket/admission recipe with a typed HTTP denial before opening signaling. This is an already documented browser limitation, not a library bug. |
| Medium | Application failures such as an occupied remote viewer become engine/session errors. | A documented adapter error-mapping hook for busy, unavailable and unsupported operations, without leaking native messages or credentials. |

These are opportunities to reduce consumer adapter code. This integration has not
demonstrated a signaling implementation defect in fastapi-webrtc 0.1.0.

## Proposed issue: declarative Canon admission errors for WebRTC

Suggested title: **Add Canon integration for WebRTC admission error contracts**.

`fastapi-webrtc 0.1.0` exposes `WebRtcRouter(APIRouter)`. Neither its constructor
nor `session()` accepts Canon's `error_registry` / `raises` declarations. Canon
0.5.5 includes a Streams integration, but no corresponding WebRTC integration.

This leaves an inconsistency for consumers using the whole stack: HTTP routes
declare application failures with named `Error` constants and `raises`, while a
WebRTC session factory appears to need local `try/except` / `HTTPException`
translation for the same application failure.

The runtime mapping already works through the composed Canon registry and the
installed Starlette WebSocket denial response support. Maximus now registers
`BrowserNotFoundError` as `BROWSER_NOT_FOUND` in the browser presentation registry.
The session factory simply calls the application service. Missing, foreign-account,
foreign-login and disabled tabs produce a pre-accept HTTP 404 problem with
`code="browser_not_found"`; media is never started. A feature contributing only
the WebRTC router must supply its error registry explicitly to `Feature`.

Requested upstream behavior:

- Provide a Canon WebRTC integration accepting an error registry and router/session
  `raises` declarations, including failures reachable through dependencies.
- Reuse the exact Canon `Error` objects and validate registry membership, rather
  than introducing a second collection of HTTP error definitions.
- Publish declared admission failures in the generated WebRTC contract. These are
  WebSocket operations, so ordinary HTTP OpenAPI route responses are insufficient.
- Keep HTTP admission problems before acceptance distinct from protocol errors
  after acceptance. In-session failures must not attempt an HTTP response.
- Document the browser WebSocket API's limited access to failed-handshake HTTP
  bodies. Contract metadata alone cannot make those bodies readable; a typed
  ticket/preflight flow could be an optional separate recipe.

Suggested acceptance tests: handler and dependency failures return the registered
problem status/code/type before any peer allocation; undeclared registry members
are rejected during configuration; generated contract checks cover admission
metadata; errors after acceptance retain WebRTC protocol framing and teardown.
As with Canon HTTP routes, `raises` should document failures rather than become
an implicit runtime exception allowlist.

This is a missing declarative integration, not evidence that consumers must keep
exception translation inside their session factories. The focused Maximus follow-up
passed 30 Python regression tests, typing, Pylint at 10.00/10 and changed-file Smelt
checks. Browser execution is recorded separately below.

## RPCKit sockets and CDP typing

Hermes now uses `@browser_channel.socket`, `RpcSocket` and `RpcService.socket`,
declaring `RpcSocketProtocol(name="cdp", version="1.3", encoding="json")`. The
contract publishes this under `x-rpckit-sockets` with a specification reference.

`hermes_client.codegen:cdp_binding` uses the new binding API. Generated
`rpc.browser.cdp(...)` returns a `CdpTransport` context; cdpify provides typed
commands, responses and events above it. The binding releases the transport reader
before closing its socket. A small frame interface and configurable connection
errors keep the transport independent of generated RPC code, avoiding an import cycle.

Native CDP text framing, authentication and tab ownership remain intact.
`RpcSocket[Incoming, Outgoing]` JSON dispatch would require an authoritative CDP
envelope model; metadata alone does not validate messages. A maintained cdpify
RPCKit binding would let consumers reuse the transport and its cleanup semantics.

The generated Python socket factory retains the earlier typing mismatch between
its `url` argument and websockets' `uri`. The existing narrow generator override
now follows `sockets.py`. A positional-only factory argument upstream would remove
this mismatch. Generated code remains unmodified.
